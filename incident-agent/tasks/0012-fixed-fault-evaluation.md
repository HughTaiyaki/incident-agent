## 3. 开工前要补的缺口（只改 Agent，不碰商城）

这些是这次核对发现的，不补的话评测测不出真实能力：

| 缺口 | 影响 | 计划 |
| --- | --- | --- |
| 提示词没告诉模型可以按 `severity`、`event_name`、`order_id`、`operation_id` 等过滤日志 | 查询程序支持这些过滤，但模型不知道，只能拿窗口内最早的 100 条，错误可能排在后面 | 写入查询说明。只改提示词，范围校验不变 |
| 回放 Bundle 最多 16 个条目 | 5 个服务的日志和 Trace，加 9 个指标，放不下；回放时查询落空，模型只能看到失败 | 放宽评测包上限，或改成按服务分条目。需校验大小 |
| 没有采集器 | 上游报告没有逐场景时间和 Trace ID | 新增采集步骤：记录实验起止时间，立刻冻结三源数据并写 manifest |
| Jaeger 只存内存 | 重启就丢 Trace，10 月的实验已无 Trace | 每次实验后立刻冻结；采集前确认 Trace 可读，否则该样本作废重采 |
| 没有泄题扫描 | 日志可能带测试名或注入提示。对 10 月 27 日实验窗口试查：`failpoint`、`TestFault`、`T3` 都是 0 条；`fault` 的命中来自 `pool=default`，是误报 | 冻结时扫描模型可见的内容，命中的样本先人工判断，可疑就重采；对各组输入一致处理，不为提分删反例 |
| 没有评测运行和判分记录 | 无法复现结果 | 新增离线评测入口，逐次保存结果、Token、停止原因和判分理由 |

这些改动走正常发布检查，用已有的匿名样本和模拟模型测试。工具是 `incident-eval`：`capture` 采集并冻结，`derive` 生成缺证据样本，`investigate` 运行调查且不覆盖已有结果，`sheet` 生成判分表。

**试运行（2026-11-02，10 月 27 日历史窗口，不计入评测）：** 采集 77 个条目，约 1 秒。日志过滤写入提示词后，模型首次给出 DIAGNOSED（2 次都是，约 13,000 Token），但主假设只描述了错误爆发和恢复，没有说出原因。这个窗口的 Trace 已丢失，也没有真值，所以不能算成绩。

4. **逐个运行实验：** 每次只跑一个场景，以便得到准确的时间边界：

   ```bash
   GOFRAMESHOP_FAULT=1 go test ./tests/fault/ -run '^TestFaultTrade$/^T3$' -count=1 -timeout 20m -v
   ```

8. **清理：** 删除临时 clone 和实验目录（内含密码副本）。Docker 容器保持现状，由你决定。

## 8. 风险

- **样本不可诊断：** T3、T7 都是瞬时故障，日志正文被省略，可能人也判断不了。这种结果本身有效，处理方式是降低粒度或增加结构字段，后者可能需要商城改动，到时另行审查。
- **崩溃丢数据：** T7 的进程崩溃可能丢失未导出的 Span 和日志，要如实标注，不能补。
- **数据污染：** 所有实验共用同一环境，靠时间窗口隔离，窗口之间要留足间隔。
- **保留期：** Loki 和 Prometheus 只保留 7 天，所以要立刻冻结，不依赖后端回查。
