## 1. 为什么换方向

[第四次复测](../docs/reports/0012-fixed-fault-evaluation.md#第四次复测harness-v14)按写定口径达到了门槛，但不能说明泛化能力：

- **一直在用看过的场景决定修改：** 没调过的留出批次 Top-1 只有 8/21，没见过的 B7 是 0/3。
- **分数混了三种收益：** 证据终于送到模型、运行更稳定、模型理解改善或记住了场景。现有评测分不开。
- **业务解释写进了通用提示词：** 它会帮已知场景拿分，也可能诱导编造，H2 的“超过 800 ms”就是例子。
- **没有基线：** 不知道动态调查比固定查询多带来多少价值。

前几轮并非白做。保留错误描述、明确查询过滤条件、修复查询拒绝、避免整份报告丢弃，都是通用的数据和工程修复，继续保留。

**今后的修改规则：** 修复必须能脱离具体场景说清楚。“比较调用方和被调用方的耗时”可以改，“遇到 goods 变慢要这样说”不行。

架构不变：单 Investigator 加确定性 Harness，不引入多 Agent 或向量库。

### 3.2 固定流程基线

名字用“固定流程基线”，避免和库存故障 B1 混淆。在 `incident-eval` 增加一个模式，放在现有 `investigate` 旁边：

- **查询：** 程序按固定规则查询，模型不选。查询清单和选 Trace 的规则在跑之前写定，不看结果，也不超过现有后端查询预算。
- **报告：** 同一模型、同一报告提示词、同样的 Token 上限和校验规则。
- **保存证据：** 保存这组证据，后面的阶段可以用完全相同的证据只重跑报告。

这样形成两种对照：

- **完整调查对照：** 固定流程和动态 Agent 用相同的冻结数据、权限、模型和资源上限，比较效果、成本和失败率。
- **相同证据对照：** 报告阶段拿到完全相同的证据，留给第 2 阶段比较关系计算、知识配置和思考模式。第 1 阶段只搭好入口，不做这些比较。

### 3.3 失败归类

每次未命中归到一类。归类依据是采样后、调查前写定的每份样本的关键记录清单：

| 类别 | 判据 |
| --- | --- |
| 运行失败 | 模型调用失败或预算耗尽，没有报告 |
| 检索失败 | 关键记录在冻结样本里，但模型没有查到或没有看到 |
| 解释错误 | 模型看到了关键记录，结论仍然错误或没有说到 |
| 证据不足 | 冻结样本里没有关键记录，比如 B1 的重复扣减 |

现在只记录 `omitted_records` 的数量，看不出模型具体看到了哪些记录。评测输出要增加每次调用展示给模型的记录 ID，不保存提示词原文。

### 3.4 实验设计（看结果前写定，之后不改）

- **样本：** 第四次复测的 22 份冻结样本，加 3 份 N2，每份每种流程 3 次。不重新采样，也不用碰商城。
- **提示词：** 两种流程相同。提示词针对这些场景调过，所以这组对比只能回答动态查询有没有增益，不能代表泛化能力。
- **判分：** 判分时隐藏结果来自哪种流程，并打乱顺序。判分标准沿用第四次复测，人工抽检比例见第 5 节。
- **接口状态：** 沿用第四次复测的探测办法，接口不健康时等待；开跑后的结果全部保留。
- **两种流程穿插运行：** 避免一种流程全部赶上接口过载。

**决策规则：** 同一份样本 3 次里至少 2 次判对，这份样本算命中，比较两种流程的命中样本数，N2 和正常样本按各自的判对标准。

| 结果 | 决定 |
| --- | --- |
| 动态 Agent 比固定流程多命中至少 3 份 | 保留动态调查 |
| 差距不到 3 份，或固定流程更好 | 默认用固定采集，只在证据缺口明确时启动动态补查 |

阈值 3 是提议的经验值，不是统计结论。22 份样本只够看方向，结果要同时报告逐样本差异、无依据断言、成本和失败率。

### 3.5 不做的事

不改提示词，不做关系计算，不开思考模式，不修因果说反，不新增场景，不碰商城。

## 4. 后续阶段

这些是第 1 阶段之后的方向，不是本次范围。第 1 阶段后用户确认的顺序：

1. 完成随机抽检，另做定向检查，两者分开记录。
2. 冻结本轮结论和两个实现。固定采集作候选默认，动态模式继续保留，不删除。
3. 做证据关系和时长计算，用完全相同的报告输入比较改造前后。
4. 加入程序驱动的补查，比较固定、动态、混合三组。
5. 用新场景验收泛化能力。

**不能提前下的结论：** 固定流程的 Token 约为动态模式的 39% 有数据支持；混合模式也只花这么多、还能弥补主要短板，目前只是预期。

**第 2 阶段：证据计算。** 调用关系已实现，线上默认关闭；[对照结果](../docs/reports/0013-call-relations-comparison.md)满足启用条件，下一步实验默认带上。实验规则见[预先写定](../docs/evaluation/0013-stage2-preregistration.md)。 程序提供可核验的关系，模型解释剩余的不确定性。

- **以 B7 为例：** 程序提供“同一调用中，调用方约 800 ms 结束并记录超时，被调用方约 1,203 ms 结束，取消错误随后出现”。模型可以提出“下游执行超过调用方的等待期限”，但这不能说明下游为什么慢，也不能推出数据库是根因。报告应该可以停在这个粒度。
- **时间先后不做硬规则：** 日志可能延迟写出，Span 常在结束时记录，跨主机还有时钟偏差。比较事件区间和明确关联；时间和语义都可靠才判矛盾，否则降低确定性。先后顺序能排除部分解释，不能单独证明因果。
- **反例先行：** 调用方先取消、下游确实变慢、重试产生多个 Span、并行调用、时钟偏差、缺少服务端 Span。这些很难在本机实验里自然出现，写成确定性的 Fixture 测试。
- **先确认字段语义：** B7 的数字显示记录的 `at` 像是 Span 开始时间，实现前要核对 Adapter。
- **思考模式：** 在这一阶段用相同证据对照测试，只开报告阶段，并依赖第 1 阶段的失败分类。此前 11 次有 10 次失败，直接重跑回答不了能力问题。

**第 3 阶段：调查与报告。** 混合流程和覆盖检查已实现，线上默认关闭；[对照结果](../docs/reports/0013-hybrid-flow-comparison.md)满足决策规则，成为第 4 阶段的候选默认。实验规则见[预先写定](../docs/evaluation/0013-stage3-preregistration.md)。这 25 份样本今后只做回归，不再用来做决定。

- **程序驱动的补查：** 最难的是发现自己漏了。H3、N1 里模型没看到关键记录，却觉得证据够了，所以补查条件主要由程序检查证据覆盖，不靠模型自评。规则不能写成“遇到 H3 就查退款”。没有覆盖规则能保证发现所有遗漏，要专门测“自信但证据不完整”的情况。

| 可观察的缺口 | 补查动作 |
| --- | --- |
| 结果被截断、某类记录没进入摘要 | 分页或定向展开 |
| 有失败调用，但缺少关联的被调用方记录 | 查询对应 Trace 或下游 |
| 有重试，但首次或后续结果缺失 | 沿操作关联补齐 |
| 有消息发送，但消费或处理结果未知 | 沿消息关联查询 |
| 报告准备断言“没有错误”，但只查了部分记录 | 收窄表述，必要时扩大查询 |

- **三组比较要记录：** 补查触发率、追回的遗漏、未触发的遗漏和实际成本。

- **关系驱动的调查：** 从异常找到关联 Trace 或业务操作，沿真实调用边和消息 Link 查依赖。关联缺失时报告断点，不靠时间接近硬拼。范围仍受权限、时间窗和查询预算限制。
- **报告拆开维度：** 观察到的现象、可支持的原因粒度、更深原因是否已知、当前状态、业务影响。现有 `recovery_assessment` 在第四次复测打印的回归和正常场景中全是 `UNKNOWN`，要查明原因。
- **校验范围：** 优先覆盖数字、单位、关联归属、状态先后和证据覆盖。自然语言因果是否充分仍要人工抽检，校验器解决不了全部幻觉。
- **系统知识独立配置：** 版本化，包含服务别名、接口映射、错误码语义、预期状态迁移和配置来源。搬到配置里本身不能消除过拟合，配置只能解释记录，不能代替本次事实。“1062 是重复键”是错误码语义，“这个接口允许幂等拒绝”是业务契约，“这次重复请求正常完成、没有影响”必须由本次证据证明。超时配置还要匹配环境和生效版本。

**第 4 阶段：泛化验收。**

- **两级测试：** 先做服务改名、单位变化等一致性测试，再用真实的新服务关系和故障变体。改名后答对只能证明不依赖名称，不能证明跨系统泛化。
- **题库不能反复用：** 看过详细结果并据此修改的留出样本，转为开发集或回归集。B7、N3 已被分析过，只能当开发案例。最终验收用新的隐藏变体。
- **静默数据错误：** 受可观测性限制，不改商城。Agent 要准确说明缺什么证据；是否给商城加对账指标，另行审查。

### 下一轮的评分口径

第 1 阶段保留写定的主指标，不重算。下一轮在运行前固定下面的口径，避免把“查不出本来没有的证据”和“有证据但没理解”混在一起：

- **可诊断样本：** 命中率。
- **不可诊断样本：** 是否正确拒答，是否准确说明已观察到的现象，是否编造了更深的原因。
- **结果方向和解释证据分开评分：** 结论对了但没有证据，不算解释正确。比如固定流程的 N1 结论对，却没看到 1062。
- **区分“请求成功”和“返回了哪个实体”：** 后者要有实体关联或明确的业务日志。
