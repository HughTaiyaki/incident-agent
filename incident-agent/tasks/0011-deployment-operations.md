# 任务 0011：部署与运维

日期：2026-11-02。状态：**工程切片已实现，本机检查和[远端 CI](https://github.com/HughTaiyaki/incident-agent/actions/runs/41326433875)通过；未在正式环境部署。** 对应[路线 P4](../docs/development/production-roadmap.md)。

## 范围

- 容器镜像、带独立 Redis 的 Compose、资源和权限限制、文件方式注入密钥。
- Worker 结构化日志、`/metrics`、告警规则、值班手册、升级回滚与备份恢复说明。
- 单个坏 Run 不再阻塞其他 Run。
- 故障演练和容量测量；密钥扫描进入发布检查。

不包含 TLS 代理、多租户认证、高可用和正式环境部署。

## 实施决定

- **坏 Run 只跳过，不丢弃。** 常驻 Worker 记录并跳过损坏、未知版本和配置不匹配的 Run；它继续占名额并告警，由人决定。`-once` 仍返回非零，便于脚本发现。这改变了之前“停止并阻塞”的决定，因为监督进程重启后会马上再次撞上同一个 Run，一个坏 Run 就等于整个服务停摆。
- **`/metrics` 用手写文本格式。** 十几个来自 Redis 的值不值得引入客户端库。指标放在 API 上，因此 Worker 崩溃时仍能报告 Worker 缺失。
- **计数器不进 Run 事务。** 改动 Lua 事务的风险不值得换取计数精确，崩溃时少记一次可以接受，Run 状态才是事实来源。
- **Redis 只开 Unix socket，容器无网络。** 不需要改客户端的 TLS 规则，也让商城或其他容器无法误连。
- **密钥走 `*_FILE`。** 环境变量会出现在 `docker inspect` 里；同时设置两种来源直接报错。
