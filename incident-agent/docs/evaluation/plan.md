# 评测与交付方案

状态：目标方案。首轮实测未达门槛，见[结果报告](../reports/0012-fixed-fault-evaluation.md)。更新：2026-11-02。商城基线与已存在实验见[接入基线](../integration/goframeshop-baseline.md)。

## 1. 三类验证不能混用

| 集合 | 目的 | 数据/执行方式 |
| --- | --- | --- |
| 诊断效果 | 根因粒度、证据支持、反例、拒答与已恢复判断 | 固定模型＋冻结真实遥测样本＋隐藏真值 |
| Harness 工程 | schema/权限/预算/取消/租约/结果未知/恢复 | Fake Provider、Fixture Adapter、可控时钟和真实 Redis 集成测试 |
| 在线端到端 | 三源关联、真实模型、告警入口、运行时间/成本、工作台 | 固定商城 SHA 的受控实例；实验操作员独立注入与恢复 |

商城 T1–T10/C1 验证交易协议；T10 是 Protobuf 兼容，不能算诊断样本；C1 重启商城不等于 Agent Worker 恢复。不得把商城 11/11 通过换算为 Agent 准确率。

## 2. 首批场景与可诊断粒度

优先利用已存在实验，不先建设另一套商城。下表是待制作的 Agent case，不声称 Fixture 或成绩已经存在。

| Case | 上游依据 | 预期证据与允许结论 | 缺失时如何处理 |
| --- | --- | --- | --- |
| D1 预留调用结果未知后恢复 | T3 | goods 的预留结果/重放、order 的未知结果/恢复、同 operation_id 和订单迁移；解释已提交而响应异常后恢复 | 缺少两端证据时仅描述重试/恢复，不断言具体网络机制 |
| D2 支付与取消竞争 | T5 | 订单状态、payment.observed、技术退款尝试及结果；区分付款成功与履约取消 | 只有退款请求日志不能确认退款完成；缺证据标未知 |
| D3 消息重投被去重 | T7/T8 | 同 event_id、publish/consume、message.redelivered；确认重复投递与幂等处理的可见迹象 | 单靠重投不可区分 ACK 丢失和生产者重发，不强判具体崩溃点 |
| D4 订单流程中断后恢复 | C1 | 中断前后业务日志、order.recover、状态收敛 | 崩溃丢 Span 时降低粒度；不得从未导出的数据臆造执行步骤 |
| D5 到期扫描兜底 | T9 | 到期状态变化、恢复链路、库存释放 | 缺少 broker 证据不得声称“队列被清空”，允许只确认扫描完成关单 |
| N1 正常业务拒绝/幂等 | T1/T2/T4/T6 | 库存不足、重复请求、迟到工作被拒绝，状态符合协议 | 防止将业务拒绝和正常恢复计作技术错误 |
| N2 证据不足/历史错误 | 冻结样本移除来源或改变合法窗口 | 声明缺失、拒绝推断当前故障 | 保留有证据的事实，不凭空补齐 |

先完成 D1、D3、N1 和证据不足切片。诊断真值标注前须由人只读同一份脱敏遥测完成排障；若人在相同范围内也不能区分，标为“细粒度不可诊断”，不能用隐藏注入点强迫模型猜中。

需要新增的场景独立排期：DB 连接争用与稳定服务延迟、持续积压、错误配置与无关变更。当前五个 failpoint 不自动等于这些故障已实现。连接争用只在证据足够时细分配置过小/慢查询，不能由 WaitCount 推断泄漏或超时。

## 3. 真值隔离与冻结样本

每个 case 的 Evaluator 元数据包括商城 SHA、case/变体 ID、负载、故障动作、注入/恢复时间、真实原因、预期信号、允许的备选解释、禁止断言、判分依据。Investigator 只看到合法告警/用户请求及查询结果。

特别防泄题：

- `utility/failpoint` 直接打印 `failpoint <名称>: <动作>` 到 stderr，`tests/fault/cluster.go` 把 stdout/stderr 合并到 work/logs；不将这些文件直接作为模型日志工具的数据源。
- 优先从实际 Loki/Jaeger/Prometheus 导出。离线读取 stdout 时只导入有效业务记录，并检查消息、异常、Span 标签、SQL 片段中是否残留测试名/注入提示；不能仅靠 JSON 解析就宣称无泄漏。
- reports 中的 fault、title、notes、violations，以及 work/config、屏障文件、数据库不变量只给 Evaluator。原始 reports 目录可能包含凭据，不能整包复制或提交。
- 对泄题记录的过滤保留审计摘要，并保持所有对照组相同输入；不能为了提高成绩删掉真正的反例。必要时重采样。
- 测试生成的业务 ID 若含 t1/t3 等特征，导出时一致匿名化并保持跨源关联；不能让 ID 编码答案。

冻结包目标：manifest（版本、窗口、schema、脱敏规则、哈希、来源状态）、Prometheus 样本、Trace 与 Link、标准化日志、查询回放规则。真值另存且不挂载给 Agent。动态查询对整个冻结数据集执行过滤/聚合，不能只为预期查询写几个固定答案。

现有 report.json 没有逐场景准确起止和 Trace ID；采集器需记录自己的时间边界与关联 ID。各次实验共用 `environment=experiment`，采集窗口、场景隔离和 ID 过滤必须防止其他实验污染。

## 4. 自动告警与短时实验

TradeRpcErrorRateHigh 要求 1 分钟至少 20 次调用、错误率 >5% 且持续 30s；TradeWorkflowStuck 要求最老工作 >30s 且持续 15s。一次触发、快速恢复的 T3/C1 不保证产生 firing 告警。

因此分开演示：

1. 人工/离线调查：明确标 manual，指定真实事件时间，评估恢复后的原因解释。
2. 自动告警调查：另建持续负载/故障场景，等待真实 firing，记录告警与入库延迟；不宣称已有 T 实验天然满足阈值。

三源入库分别做有界可见性检查。指标导出/抓取间隔与 batch 延迟需要预热和观察窗口，进程崩溃可能丢缓冲；超时记录缺失，不能靠无限等待保证样本完美。

## 5. 基线、消融与留出

对同一批冻结遥测、权限和资源上限比较：

- B0：固定查询流程＋规则判断。
- B1：固定查询流程＋同一模型生成报告。
- A：Agent 动态选择查询＋同一模型生成报告。

资源上限相同，不强迫各方法使用相同步数；记录实际耗时/Token/查询。比较 B1 与 A 才能判断动态调查的增益。若 B0/B1 更合适，保留结论。

上下文优化单独做消融，保持模型、样本、工具、预算与其他 Prompt 部分固定；报告输入 Token 变化和命中率变化，不能只展示成本下降。开发 case 与留出变体分离，变化告警入口、负载、症状原因组合和证据缺失模式，不只换时间或一句日志。

每个场景先重复三次用于冒烟和随机性观察；同 case 重复不是独立场景。小样本保存逐次结果、分子分母与耗时；P95 标样本量，不外推生产。

## 6. 指标与发布门槛

| 指标 | 分母与解释 |
| --- | --- |
| Root-cause Top-1 | 可诊断执行中，主假设同时命中组件与预先约定原因粒度；可诊断 case 的拒答算未命中 |
| Unsupported Claim Rate | 无支持的关键事实/根因断言 ÷ 全部关键断言；零断言为 N/A |
| Evidence Support Precision | 真正支持对应 claim 的引用 ÷ 全部引用；引用存在率单独列 |
| Inconclusive Precision/Recall | 正确拒答质量和覆盖；另列可诊断场景误拒答率 |
| 时间 | Run 接受到终态，另列排队/首次证据/模型/查询耗时；人工排障收益需单独有人参与的对照 |
| 成本 | 输入/输出 Token、实际后端请求、重试与未知用量；固定价格配置估算 |
| 恢复正确性 | 中断后不丢已提交证据、不超预算、不接受旧 owner 写入并到达合法终态 |
| 恢复后的任务效果 | 相较未中断的命中率变化、额外尝试与延迟；全降级不能包装成诊断成功 |
| 注入/权限 | 越权实际执行数、污染报告数、合法请求误拒绝数，各自给分母 |

硬门槛：非法查询、资源越权、伪造 Evidence ID 被拒绝；预算/取消/接管确定性测试通过；缺证据可 INCONCLUSIVE；报告提交后可重读；SSE 断线不丢最终报告。

原草稿“核心五类各三次，命中至少 12/15、Unsupported Claim Rate≤10%”只保留为候选效果目标：须先形成五类**可诊断且标注完成**的独立场景；不能把当前 T 编号凑满分母。未达到时发布实验版本并分析失败，不改真值追成绩。

## 7. 交付与故障演示

完整演示至少包含：真实证据调查、证据不足/错误案例、Worker 中断恢复、与固定流程的对照。人工处理后在同类负载和明确窗口观察错误/延迟/积压是否恢复，记录同期其他变更，反馈与原报告分开保存。

后续目标命令是离线评测、在线评测和 demo；只有脚本、依赖、退出码与报告目录实现后才加入 Makefile/README。本次不增加空壳命令。

每份可发布报告附模型配置、Prompt/策略/查询模板版本、商城 SHA、样本哈希、执行次数、停止原因、原始结果索引、人工判分理由和失败分析。模型、Prompt、工具、压缩、模板、证据规则任一改变都运行相应固定回归。

## 8. 告警、聚合和工作台的补充验收

这些场景验证本项目新增设计，不是参考项目已经证实的能力，也不自动增加“可诊断故障类别”的分母。

| 维度 | 对照或故障输入 | 验收依据 |
| --- | --- | --- |
| 告警幂等 | 同 episode 多轮／并发重放；同 observation 重试；Run 完成后继续 firing | 首个 Run 唯一；observation 计数准确；终态不被重开 |
| 告警边界 | 同服务不同 peer／step；重新激活；来源失联 | 不错并症状；新 episode 可识别；失联不报恢复 |
| 持续告警 | 可控时钟跨越去重保留期，持续刷新 | 不因 TTL 到期重复创建 Run；不靠真实等待 30 天测试 |
| 日志聚合 | 大量重复错误＋少量恢复／反例；缺失 Trace；超过 100 条 | 样本计数标注；代表记录可展开；遗漏信息可见 |
| 聚合消融 | 其他条件相同，仅改变聚合／展开策略 | 同时记录输入／输出 Token、工具请求、命中率、证据支持与误拒答 |
| 来源质量 | HTTP 200 空结果、超时、截断、安静服务、保留期缺失 | EMPTY 与未知覆盖并存；不把无日志或旧时间直接判正常／采集故障 |
| 证据回查 | 原后端过期；新查询返回迟到数据；跨 Run 引用 | 保留期内快照可读，过期明确；新结果不改原报告；归属校验生效 |
| 交付闭环 | SSE 重连、报告提交后 Worker 中断、人工外部处置与验证 Run | 持久报告可重新获取；新旧窗口分开；反馈与原结论分开 |

聚合试验需记录冻结数据本身的采样来源，不能只在人工挑选的几条日志上声称可扩展性。报告所有比较组的实际失败和拒答，不删除对压缩不利的样本。

恢复成功继续以状态／证据／预算不变量衡量；另统计恢复后 DIAGNOSED、INCONCLUSIVE、FAILED 的数量与诊断质量变化，避免把全部降级都包装成有效诊断。

业务效率如需测量，应让参与者在可比场景中分别使用原遥测工具和工作台，平衡场景顺序、避免同一答案记忆影响，记录完成时间、结论质量和参与人数。没有这项实验时，只报告系统执行成本，不声称降低人工成本。
